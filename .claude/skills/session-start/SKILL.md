# Старт работы над игрой

Это не веб-приложение: базы нет, серверной логики нет. Есть Go-обёртка, которая
отдаёт статику, и вся игра — файлы в `static/game/`.

## 1. Прочитай перед первой правкой (именно в этом порядке)

1. `docs/brief.md` — бриф и концепт. **Нет файла или пустые разделы** → идёт
   фаза Бриф → Концепт: заполняй по шаблону файла, поля «целевая эмоция»,
   «почему игрок вернётся», «что делает игру честной» оставляй человеку.
   Код НЕ пишем, пока в брифе не стоит «Статус: концепт утверждён».
2. `static/game/config.js` — `window.ZV_GAME`: `title`, `archetype`, `brand`.
   Показывает, какой кит уже выбран и какие цвета бренда доступны.
3. `static/game/kits/<archetype>/README.md` — что в ките настраивается и где.
   Читай README до чтения `kit.js`: там карта параметров.
4. Скилл своего архетипа: `archetype-runner` / `archetype-catch` /
   `archetype-quiz`. Дальше — `mobile-contour`, `assets`, `ready-checklist`.

Не читай `static/vendor/` — это движок, он тебя не касается.

## 2. Как проверить, что не сломал

```sh
go build ./... && go test ./...
```
Тесты шаблона ловят ровно то, что не видно на глаз: битые ссылки в html/css/js,
внешние адреса (их быть не должно), синтаксис всех `static/**/*.js`,
валидность `config.js` и известный `archetype`, ответы обёртки (`/` → 200 html,
картинка → 200 в base64, чужой путь → 404), упоминания платформы в статике.
Красный тест — чини сразу, не «потом»: превью соберётся из сломанного кода и
человек увидит белый экран.

Живая проверка своими руками:
```sh
go run ./cmd/server >/tmp/game.log 2>&1 &
curl -sf localhost:8080/ >/dev/null && echo ok
```
Открой ключевые пути (`/`, `/game/main.js`, спрайт из `/assets/`), посмотри
`/tmp/game.log`, погаси процесс. Ошибки JS так не поймать — их ловит человек с
телефона, поэтому после каждой заметной правки сохраняй код и зови смотреть
превью (в панели превью есть QR «на телефоне»).

## 3. Порядок работы

Прототип **на заглушках** — киты рисуют фигуры сами (`makeRect`/`makeCircle` в
`preload`), картинки не нужны. Баланс крутим на фигурах: это только ходы, а не
кредиты. Картинки заказываем один раз, когда игра уже интересна (скилл
`assets`). Каждая заметная правка: собрал → тесты → сохранил (`git add -A &&
git commit && git push`) → позвал смотреть превью.

## 4. Чего НЕ делать

- **Не трогай `static/vendor/`** — движок лежит локальной копией нужной версии
  (лицензия в `LICENSE-phaser`). Не обновляй, не минифицируй, не переименовывай.
- **Никаких CDN и внешних скриптов/шрифтов/стилей.** Всё, что грузит страница,
  либо лежит в репозитории, либо это URL картинки из файлов проекта. Внешний
  `<script src="https://...">` — сразу отказ: игра встраивается на сайт бренда,
  сторонние запросы там недопустимы.
- **Не упоминай платформу и вендоров** — ни в `title`, ни в мета-тегах, ни в
  видимом тексте, ни в комментариях и `console.log`. Игру смотрит конечный
  игрок бренда. Есть grep-тест, но не доводи до него.
- **Не добавляй Go-зависимости и не заводи второй `package main`** в корне:
  сборщик функции требует ровно один. Логика игры — только JS.
- **Не переизобретай мобильный контур** (портрет, масштаб, звук по первому
  тапу, экраны) — он в `shell.js`, скилл `mobile-contour`. Правки контура
  ломают запуск на iOS тише всего.
- **Не генерируй картинки, пока концепт не утверждён** — это деньги человека.
- Не пиши в `docs/brief.md` за человека поля, помеченные как его.

## 5. Язык с человеком

Он продюсер игры, не программист. Не говори «сцена Phaser», «физическая
группа», «спрайт-лист», «коммит». Говори: «экран», «персонаж», «набор кадров»,
«сохранил». Спрашивай только продуктовое: приз, длина партии, что собираем,
чего избегаем. Технические решения принимай сам.
